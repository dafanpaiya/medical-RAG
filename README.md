# 医药知识问答系统 | Medical & Life Sciences RAG

一个面向医药知识场景的检索增强生成（RAG）项目。

项目围绕医药专业知识检索、证据约束回答、药典数据处理和知识边界控制展开，重点探索如何让大语言模型在专业知识问答中更可靠地使用外部知识，而不是仅依赖模型自身记忆生成答案。

**项目定位：个人技术工程验证项目**

> **项目成熟度声明**
>
> 本项目用于**研究与技术能力展示**，不是经过认证的医疗器械、临床决策支持系统，也不能替代专业医疗、质量管理或法规审查。
>
> 当前知识库包含从**网络获得的《中国药典》2025 年版相关扫描件 PDF 经 OCR 和后续处理形成的候选数据**。当前索引覆盖范围并**不等同**于整部药典的完整、权威数字化版本。使用者应以正式出版物及监管机构发布的原始文件为准。如果**涉及版权或其他合法权益请联系项目作者处理**。

## 1. 项目背景

通用大语言模型可能产生幻觉。在药品监管、医药研发和专业知识查询等高风险专业场景中，错误或缺乏依据的回答可能造成严重影响。

本项目尝试通过 RAG 技术建立一套以外部知识证据为基础的问答流程：

- 从专业知识库中检索与问题相关的内容。
- 对检索候选进行相关性和专业实体边界控制。
- 将检索到的证据用于回答生成。
- 根据检索结果及相关性条件决定是否生成回答；在部分证据不足的场景下触发拒答。

## 2. 核心功能与工程特性

### 2.1 专业知识检索

- 结合向量检索与词法匹配获取相关候选内容。
- 使用 256 维双语字符与 n-gram 子词哈希向量表示文本。
- 对向量进行 L2 归一化，并使用余弦相似度进行相似性计算。
- 结合专业术语、实体信息及候选重排序改善检索结果。
- 支持检索阈值和查询扩展策略配置。

当前向量实现属于基于字符与子词哈希的向量表示，并非由 Transformer 或预训练语言模型生成的语义嵌入。

### 2.2 药典实体边界控制

针对药典不同品种、各论及通则之间可能出现的内容混淆，项目引入实体边界识别和候选重排序机制。

目标是降低不同专业实体之间的错误匹配和证据串扰。

对于知识库中尚未满足证据要求、存在隔离状态或无法确认来源归属的内容，系统在相应处理路径中限制其作为可靠证据使用。

### 2.3 证据约束与拒答机制

- 根据检索结果及相关性条件判断是否具备回答依据。
- 在部分证据不足、知识库未覆盖或来源边界不匹配的场景下触发拒答或人工升级。
- 对无法提供可靠来源依据的内容，尽量避免生成确定性结论。
- 支持本地确定性回答合成路径，在没有可用 API Key 时使用本地生成逻辑。

本地回退路径不等同于调用另一个大语言模型，也**不能**保证回答完全没有事实错误。

### 2.4 安全与数据边界

项目实现了规则驱动的输入与输出安全检查：

- 使用中英文规则模式识别常见提示注入、越狱及指令覆盖表达。
- 对规则生成可容忍常见空白和分隔符变化的匹配变体。
- 对用户输入进行结构和长度校验，最大查询长度为 500 个字符。
- 将用户输入作为不可信数据处理，通过明确的数据边界降低其干扰系统指令的风险。
- 对生成结果执行预设系统提示指纹检查。
- 提供请求频率限制机制。

上述机制属于规则驱动的安全措施，不能保证识别或阻止所有提示注入和信息泄露攻击。

**引用检查限制：** 当前代码包含引用存在性检查逻辑，但该逻辑存在缺陷：当检索引用列表非空时，即使回答中没有匹配到文档标题或管辖区域，也可能通过检查。因此，当前检查**不能**作为回答引用完整性或事实准确性的保证。

### 2.5 用户反馈与人工协助

提供以下 REST API：

| API | 功能 |
|---|---|
| `POST /api/feedback` | 提交回答评价、反馈标签及评论 |
| `GET /api/feedback-metrics` | 获取反馈统计 |
| `POST /api/escalate-to-human` | 提交人工协助请求 |

反馈记录通过 JSONL 格式保存在本地文件中，并提供点赞、点踩及反馈标签统计。

人工升级请求会生成工单标识，并记录相应审计事件。

项目还包含专家处理结果进入知识库的相关逻辑，但不将其描述为已经验证的完整自动学习或专家审批闭环。

### 2.6 知识库完整性与启动校验

当前应用启动时使用统一知识库引擎，并对关键知识库文件执行完整性检查：

- 对候选知识库文件执行 SHA-256 校验。
- 对企业基线知识库执行独立 SHA-256 校验。
- 检查企业基线文档及向量的一致性。
- 检查知识库组成信息及来源冲突报告。
- 关键文件缺失、无法读取或校验不匹配时拒绝启动。

该机制用于验证指定知识库文件是否符合预先批准的基线，不代表知识库内容本身已经被证明完全正确。

### 2.7 本地运行与模型配置

项目支持本地 Python 服务运行，并提供不依赖外部模型 API 的确定性回答回退路径。

模型 API Key 从后端环境变量读取，也支持请求级 API Key 参数。具体行为取决于当前环境配置和代码执行路径。

## 3. RAG 技术流程

```text
用户问题
   │
   ▼
输入校验与安全检查
   │
   ▼
问题预处理
   │
   ▼
查询扩展 / 专业术语处理
   │
   ▼
混合检索
   ├── 哈希向量相似度检索
   └── 词法匹配
   │
   ▼
候选结果合并
   │
   ▼
专业实体边界控制与重排序
   │
   ▼
证据相关性判断
   │
   ├── 证据不足 / 边界不匹配
   │          │
   │          ▼
   │       拒答或人工升级
   │
   └── 证据满足相应条件
              │
              ▼
          答案合成
              │
              ▼
       生成后安全检查
              │
              ▼
       引用检查与结果返回
```

该流程体现了项目的核心设计思路：先检索和评估外部证据，再决定是否生成回答。

注意：当前引用检查存在已知逻辑缺陷，不能据此认为系统已经完成严格的逐条事实与来源一致性验证。

## 4. 知识库与数据处理

### 4.1 中国药典 2025 年版数据

项目包含从《中国药典》2025 年版相关扫描件 PDF 处理形成的候选知识库。

当前候选知识库包含：

- 12,089 条文档切片（chunks）。
- 对应的 12,089 条向量数据。
- 256 维向量表示。

以上为当前候选知识库的数据规模，不代表四部药典的全部内容均已完整覆盖，也不代表 OCR 结果已经达到正式出版物的准确性。

### 4.2 PDF 解析与 OCR

项目包含基于 PyMuPDF 和 RapidOCR 的 PDF 页面文字识别流程：

- 使用 PyMuPDF 读取 PDF 页面并执行页面图像渲染。
- 使用 RapidOCR（ONNX Runtime）执行页面文字识别。
- 支持页面 OCR 缓存及批处理流程。
- 对识别结果进行后续文本处理和文档切分。

OCR 结果可能受到扫描质量、页面排版、表格结构、特殊符号和字符识别准确性的影响。

这里描述的是项目的数据摄取与处理能力，不代表用户每次通过 Web/API 提问都会实时执行 PDF OCR。

### 4.3 文档切分与表格处理

项目在药典数据处理流程中区分不同类型的内容：

- `TEXT_CHUNK`：普通文本内容。
- `TABLE_CHUNK`：表格内容。
- `AUXILIARY_CHUNK`：辅助内容。
- `SECTION_CHUNK`：进一步处理形成的章节内容。

表格内容保留相应元数据。对于表格结构尚未解决的内容，摄取流程实施隔离，向量存储也会拒绝将特定未解决结构的表格直接作为普通文本索引。

这有助于降低表格内容在丢失二维结构后被错误解释的风险，但不代表所有表格都已成功恢复为完整的结构化数据。

### 4.4 知识库完整性

系统对指定知识库文件执行 SHA-256 完整性校验，并在当前统一知识库启动路径中验证候选知识库及企业基线。

当关键校验不通过时，系统拒绝启动，而不是静默加载未经批准的知识库文件。

## 5. 检索参数

当前项目的检索参数包括：

| 参数 | 当前配置 | 作用 |
|---|---:|---|
| `top_k` | 6 | API 查询路径的默认初始候选数量 |
| `top_n` | 3 | API 查询路径的默认重排序候选数量 |
| `RAG_SCORE_THRESHOLD` | 0.40 | 候选相关性阈值 |
| `RAG_EXPANSION_MODE` | `BASELINE` | 查询扩展策略 |

向量表示采用 256 维双语字符与 n-gram 子词哈希方式，并结合 L2 归一化和余弦相似度。

参数的实际效果取决于检索算法、知识库内容和查询类型，不能将单一阈值或检索数量视为所有医药问题的通用准确性保证。

## 7. 本地运行

### 环境要求

- Python 3.10 或更高版本。
- Windows 环境可使用仓库提供的启动和停止 BAT 脚本。
- 需要安装项目依赖。

### 安装依赖

```bash
pip install -r requirements.txt
```

### 配置环境变量

根据项目提供的 `.env.example` 创建 `.env`，并根据实际使用的模型配置填写相应环境变量。

主要配置项包括：

| 环境变量 | 作用 |
|---|---|
| `GEMINI_API_KEY` | Gemini API Key，可选 |
| `HOST` | 服务监听地址 |
| `PORT` | 服务端口 |
| `RAG_SCORE_THRESHOLD` | 检索相关性阈值 |
| `RAG_EXPANSION_MODE` | 查询扩展策略 |
| `UNIFIED_KB_PATH` | 统一候选知识库路径 |

### 启动服务

Windows 用户可运行：

```bat
启动项目.bat
```

停止服务：

```bat
停止项目.bat
```

默认服务地址：

```text
http://127.0.0.1:8000
```

具体 API 路由及使用方式以当前项目代码为准。

## 8. 已知限制与后续方向

### 当前限制

1. **知识库覆盖范围有限**

   当前候选知识库并非《中国药典》2025 年版四部内容的完整数字化索引。未覆盖内容无法保证检索结果。

2. **OCR 质量限制**

   扫描文档中的表格、化学符号、特殊字符和排版结构可能影响文本提取及后续检索。

3. **引用检查存在缺陷**

   当前引用存在性检查在检索引用列表非空时可能无条件通过，不能保证回答实际包含有效引用，更不能证明回答中的每条事实均受到原始证据支持。

4. **规则驱动的安全防护存在边界**

   提示注入检测依赖预设规则及其变体，无法保证覆盖所有攻击方式。输出指纹检查也不能替代全面的信息泄露检测。

5. **哈希向量的表达能力有限**

   当前向量表示基于字符与 n-gram 子词哈希，不等同于预训练语义嵌入模型，其语义表达能力和检索效果存在局限。

6. **本地运行架构**

   当前系统采用本地 Python 进程运行方式，尚**不能**据此宣称具备大规模企业级分布式部署能力。

7. **反馈与专家处理闭环仍需验证**

   项目包含反馈记录、人工升级及专家处理相关代码，但**不能**据此认定完整的专家审核、审批和知识库持续更新流程已经通过端到端验证。

### 后续方向

- 扩展和验证药典各卷知识覆盖范围。
- 改进 OCR 质量及表格结构恢复。
- 修复并测试引用检查逻辑。
- 增加自动化检索与答案质量评估。
- 完善端到端回归测试。
- 根据实际负载评估更适合的向量检索及部署方案。
- 完善反馈、人工审核与知识库更新的闭环验证。
